# Editorial Memory — lessons from edits, not imaginary cross-session memory

Editorial Memory is a separate, **optional private** record of rules approved by the writer. It captures *why* an earlier draft was rejected, beyond surface tone. It is not an automatic server-side memory or an excuse to store a user's posts without consent.

## Extract from real revisions

When the author provides an AI version and their final edited / posted version:

1. Identify differences in **thesis**, **evidence/mechanism**, **structure**, **voice**, **format**, **level of research** and **account routing**. Don't mix a one-off campaign requirement with a lasting personal preference.
2. Infer one narrow, testable **PROPOSED** preference, backed by a source draft ID, feedback and date. Example: “For market structure Articles, start with a verifiable mechanism rather than a generic market overview.”
3. Present the candidate rule for explicit author approval. Reject contradictory evidence or note context conditions; avoid “this person always” from one sample.
4. If approved, store only at a **user-authorized private path**, e.g. `~/.claude/editorial-memory/<author-id>.md`, never under public repo or shared ZIP. Without consent, use in the current session only; don't imply persistence.
5. Apply approved rules to relevant future drafts, but allow today's explicit instruction to override. Keep a visible revision log so the author can undo or update preferences.

## Priority

Explicit instructions for current request > approved Account Profile / hard red lines / official source status > approved author stance > author's final published edit > approved Editorial Memory > evidenced Voice Profile > temporary writing-mode defaults > peer craft inspiration.

Never use one author's Memory for another author or apply a personal preference to an official account without authorization. Retain sensitive/private data minimally, avoid embedding full private post texts, and keep the author able to revise the rule.
